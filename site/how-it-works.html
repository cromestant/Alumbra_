How Alumbra works

You point your phone, ask a question out loud, and hear an answer that says where things are: "the mug is at your 2 o'clock, about a meter away". This page explains what happens in between, and which model does which job.

The idea in one paragraph

Models are good at seeing and describing. They are less reliable at exact positions, and on safety questions a mistake can hurt someone. So Alumbra splits the work. Models perceive: they name what is in the scene, find each object's outline and write the wording. Code decides: it turns outlines into clock directions and distances, works out whether a path is clear, and adds hazard warnings. Questions that must not be answered by a model alone, such as whether to cross a street, go to a human volunteer.

The models

One ask, end to end

The three flows

A. Open scene

"What's in front of me?" "Is the path clear?" Spark names everything it sees, SAM locates each name plus the safety list.

B. Find a named thing

"Where are my glasses?" SAM searches for the named thing directly, plus the safety list.

C. Read a label

"Which one is the ibuprofen?" SAM finds the bottles or boxes, each one is cropped, and Spark reads its label.

Where the time goes

A typical ask takes 25 to 35 seconds. Below is a real count question ("How many mailbox banks are there?"), measured on November 2, 2026. Bars that overlap ran at the same time.

Three things keep this down:

  • Work that doesn't depend on anything starts at once. Naming runs while a spoken question is transcribed; a count's own search runs during naming.
  • Searches run in parallel. All the SAM searches for one ask go out together.
  • Slow calls get a backup. If one SAM search hasn't answered after 8 seconds, an identical copy is sent and the first answer wins. Normally a search takes about 2.6 seconds, but rarely one hangs for over a minute and holds up the whole ask.

Path questions

"Is the path clear?" and "Can I get to the door?" get extra care, because a wrong "yes" is the worst possible answer.

  • The verdict is computed, not written by a model. The code finds the goal (or straight ahead), draws the corridor you would walk through, and checks which objects stand on the floor inside it.
  • The floor gets its own look. Small things on the floor (a toy, spilled ice) are easy to miss in a whole-scene view, so likely floor areas are cropped and read separately.
  • Doors are checked for the opening. The door leaf is not the way through; the gap is.
  • Darkness is measured. If the photo is too dark, Alumbra will not say the way is clear. It says it can't tell.

Distance

With the phone's tilt and focal length, distance comes from geometry instead of guesswork:

  • Things on the floor: the ray from the camera to the bottom of the object meets the floor at a distance set by the phone's height and tilt.
  • Doors, people and cars: their usual real height, compared with how tall they appear, gives the distance.

Distance only changes how far things are said to be and the order they are mentioned. It never decides whether something counts as a hazard.

Follow-up questions

After an answer you can ask a follow-up ("how far is it?") without taking a new photo. The server keeps the ask's scene for up to an hour, so a follow-up skips the naming and searching and only runs the new parts.

Access in this test version

This is a test app, so there is no account. On first use the app registers itself with the server and receives its own token. Each phone can make 10 asks every 5 minutes, follow-ups included, and the server caps the total number of phones and asks per hour. A real release would use proper sign-in and app attestation instead.
