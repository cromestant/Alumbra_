Roadmap

Ideas that came out of testing and measurement but are not built yet. Each one says why it matters and what it would cost.

Seeing more, more reliably

Fall back to a general word when a search finds nothing

Asked "Where is my ragdoll?", SAM found nothing under the word "ragdoll" (a cat breed). Spark, looking at the photo, placed the cat correctly, but that position was unmeasured. Asked "How many mailbox banks?", Alumbra once said there were none, because the specific phrase matched nothing.

Plan: as soon as the question is known, ask a fast model for the everyday word ("ragdoll" → "cat", "mailbox bank" → "mailbox"). If the specific search finds nothing, search for the general word, and report what it finds under the user's own word.

  • Cost: no added time when the first search succeeds. About 4 seconds on a "where is" miss; none on a count miss, which finishes during naming.
  • If it finds several ("two cats"), say so rather than guess which one.
  • If nothing is found at all but the answer model sees it, say the position is a rough one ("I think it's at 10 o'clock, but I couldn't locate it exactly").

Combine two models' lists of what is in the scene

Spark and the Baseten model each miss objects the other names: a fire hydrant on a sidewalk, a path through a garden, a charging cable on a desk (benchmark). Baseten's list arrives about a second sooner, so searching both lists together adds little delay. Objects only one model named would still be located by SAM, and a wrong name is dropped when the search finds nothing.

  • Cost: one extra model call and about 5 more searches per ask.

Use more of a video clip

A clip ask once missed apples that were visible in the clip but not in the middle frame used for naming. Options: name objects in several frames, or pick the sharpest frame instead of the middle one.

Skip the standard hazard searches on count questions

Every ask searches for cars, people, stairs, doors and curbs. A count question doesn't use them, so skipping them would save about 5 searches. To be done carefully: those searches exist for safety.

Speed and cost

  • Settle disagreements in model races. The Baseten model wins most floor-read races by speed but has mislabelled spilled ice as "teeth". Options: use Spark's reading when the two disagree, or report a hazard only when both agree.
  • Drop a race that never helps. On path answers both models always added nothing; that call can probably go.
  • Stop paying for losing calls. When a race or a backup search is decided, the losing call keeps running and is still billed.
  • Don't name the scene for "where is" questions. With a spoken question, naming starts before the question is known, and a "where is" question then throws it away (10.5 seconds of model time in the first live ask).
  • Revisit the final polish step. It only runs on long drafts, which live asks rarely produce.

Toward a real release

This version is a test build. A public release would need:

  • Accounts and app attestation (for example Play Integrity) instead of the test app's self-registration and per-phone limits.
  • A real volunteer service: volunteer accounts and vetting, notifications that reach volunteers wherever they are, and cases that survive a server restart.
  • Persistent follow-ups with a clear retention policy, instead of in-memory storage.
  • Play Store distribution, with a release build signed for the store.
  • Testing with blind and low-vision users across many more scenes, lighting conditions and phones.
